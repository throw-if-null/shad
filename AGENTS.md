# AGENTS.md

## Project overview

`shad` is a Python CLI tool that manages project-specific tmux sessions. It creates a tmux layout per project — opencode and bash, plus a git panel and a todo pane that are on by default and can each be turned off — and handles session lifecycle: open and status per project, and save, restore and stop across projects. Configuration lives in `~/.config/shad/shad.toml`; todo files live in `[todo] path`, or in the per-OS data directory when it is not set.

Entry point: `shad.cli:main` (registered as the `shad` console script).

## Architecture

The codebase follows a **vertical slice** layout — each CLI subcommand owns its own package under `src/shad/`:

Key data flow for the main `open` command:
1. `projects/command.py` resolves the project name (supports prefix matching)
2. `projects/open/sessions.py` shows a picker over the conversations `harness.py` finds on disk
3. `projects/open/command.py` resolves the tmux session name through `tmux.py`, creates or reattaches
4. `layout.py` builds the tmux layout: opencode, bash, and whichever of the git panel and the todo pane are enabled

## Conventions

- **Python 3.11+** with `from __future__ import annotations` in every module.
- **No external deps** beyond `rich` (printed output) and `textual` (the git panel, the one
  full-screen app). `textual` depends on `rich`; it does not replace it, and the commands that
  print and exit stay on `rich`. tmux interaction is via subprocess calls.
- Tests live **next to the code** they test (e.g. `command.py` + `test_command.py` in the same directory).
- Test framework: `unittest` (stdlib), run via `pytest`.
- Linting: `ruff check src/`
- Type checking: `mypy src/`
- All three checks run in CI and can be run locally via `make check`.

## Testing

```sh
make test       # pytest
make lint       # ruff
make typecheck  # mypy
make check      # all three
```

Tests are `unittest.TestCase` classes. A command's tests run it through the entry point and assert its contract: the exit code, both streams or the screen, and the files and tmux sessions it changes. The Feature and Boundary lines of the behavioral verification protocol sit on the test class; each acceptance criterion sits in the docstring of the test that asserts it, and the test is named after it. The unit tests of the modules behind a command use `unittest.mock.patch` to isolate subprocess and I/O calls. No conftest files. Shared test support is `src/shad/testing.py` and a slice's `testing.py`; no command imports either.

`src/shad/testing.py`:

- `run(argv, env=...)` calls `cli.main` in this process and returns the exit code, stdout and stderr. A `None` value in `env` removes the variable for the call.
- `TmuxCase` gives a test a tmux server of its own and a temporary home, config and data directory. The server listens on a private socket under `/tmp`; the fixture passes `-S` and `-f /dev/null` on its own calls and sets `TMUX_TMPDIR` for the processes it starts. Neither the server nor a process a test starts inherits `TMUX`, `KITTY_WINDOW_ID`, `KITTY_LISTEN_ON`, `VISUAL` or `EDITOR` (`UNSET`): `sessions restore` would open real kitty tabs, and a command would open the user's editor. A command that drives tmux or needs a terminal is tested there, never against the user's server. A `shad` shim on `PATH` runs this checkout, and the panes a shad layout creates inherit the server's environment.
- `pane(*args)` runs `python -m shad` in a window of that server under a real pseudo-terminal: `send`, `type`, `wait_for`, `screen`, `wait_exit`. The pane keeps the `TMUX` that tmux sets for it.
- `run_detached(*args)` runs shad as a process with no controlling terminal, which is how the no-terminal paths are tested.
- `shell_with_client()` opens a `shell` session with a real nested tmux client attached. A command typed into it with `type_into_shell` runs as a user runs it, and `wait_for_client_on` watches which session the client lands on, which is how attach and `switch-client` are tested.
- `fake_harness("claude")` puts a sleeping `claude` on `PATH` whose pane reports `claude` as its foreground command.
- `deps(cfg)` is the `Deps` a unit test hands a slice's `run` directly: `cfg` stands in for the file, and nothing is read.
- `FakeEditor` is an `$EDITOR` that is a real program: it records each file it is given, saves a scripted draft over it, and exits with a chosen status.

CI installs tmux for this.

## Common pitfalls

- **tmux session naming**: bare project session name (e.g. `tin-shad`) is for new/default sessions. Scoped names use the pattern `<base>--<prefix>-<session-id>`, where the prefix is `oc` for opencode and `cc` for Claude Code. `tmux.py` owns the table (`SESSION_PREFIXES`), builds the name (`project_session_name(base, prefix, key)`), and splits it again (`split_session_name()`); `shad sessions` depends on the round trip.
- **`shad projects <name>` opens a new conversation by default**: `open_project` builds a `Target` from the flags — `fresh_target` (the default, no picker), `resume_target` for `--resume <id>`, the most recent recorded conversation for `--resume` with no id, or `pick_target` for `--pick` ([CLI-6]: no picker without the flag). `--pick` with no terminal raises `no_terminal`; a cancelled picker returns None. A fresh `Target`'s key is unique (`fresh-<hex>` for opencode, a fresh uuid for claude), so its session never already exists — `open_project` only probes `session_exists` and attaches for a resumed or picked conversation. There is no kill-and-recreate branch.
- **A picker must resolve a real session id**: the tmux session name is derived from `session_key`, so a picker that returns a constant key maps every resumed conversation onto one tmux session, and a second `shad projects <name>` attaches a second client to it. tmux mirrors one session across its clients, so both terminals then drive the same harness process. This is why the picker resolves a real id and `resume_target`/`fresh_target` build `claude --resume <id>` / `claude --session-id <uuid>` instead of handing the choice to `claude --resume`. A new Claude Code conversation gets a uuid shad chooses, passed as `claude --session-id <uuid>`, so its tmux name identifies the conversation too; opencode, which assigns its own id, gets a unique `fresh-<hex>` key instead. Claude Code derives `<slug>` from the project path by replacing every character outside `[A-Za-z0-9]` with a hyphen. Each row shows the session's name, then its first prompt. The prompt is the first user entry that is neither `isMeta` nor a command wrapper; a transcript with no such entry is an empty session and is not offered. The name is the last `custom-title` entry (`/rename`), else the last `ai-title`. Claude Code appends both anywhere in the transcript, so `_claude_session_name` reads the whole file, and it matches the entry type as bytes before it parses a line, because a transcript can be tens of megabytes.
- **Inside vs outside tmux**: `Tmux.attach()` uses `switch-client` when shad runs inside tmux (`TMUX` was set when the root constructed the `Tmux`), `attach-session` otherwise.
- **`shad sessions` reads Claude Code's process record, not the tmux name**: Claude Code 2.1 writes `~/.claude/sessions/<pid>.json` for each running process, with the current `sessionId`, the session's `name`, a `status` of busy or idle with `statusUpdatedAt`, and a `tmux` field of the form `<session>:@<window>.%<pane>`. `/clear` and `/resume` move a process to another conversation while the tmux name keeps the id the pane was opened with, so the record is the truth and the name is the fallback (only when its key is a uuid). A record whose pid is dead is ignored: a killed process leaves its file behind. The file is undocumented; `harness.py::_claude_process_record` is the one place that reads it. The first prompt comes from the transcript through `claude_session_title`, which reads only its first lines.
- **Harness support in `shad sessions` is a registry**: `harness.py::SUPPORTED` maps a harness name to an object with `live_conversation`, `can_resume`, `resume_command`, `fresh_command` and `new_session_id`; `KNOWN` holds opencode too, for the pickers, and `resume_target`/`fresh_target` are the one place a harness's command line is written. `live_conversation` returns a `Conversation` (id, and optional name, title, status, status age). Only Claude Code is registered. `save` lists a session of an unregistered harness with the reason and does not write it, `restore` skips its entries, and `stop` kills it like any other, because killing needs no harness. To add OpenCode, implement `live_conversation` and `can_resume` on `Opencode` (the live id of a fresh session would come from the opencode SQLite DB, by project path and creation time) and add it to `SUPPORTED`; nothing else in the slice names a harness.
- **One package per action, with crosscuts at the slice root**: in `projects/`, `config/`, `sessions/` and `todo/`, each action is a package with its own `command.py` and tests. The package's `command.py` registers the group parser and calls each action's `register`, which adds the action's parser through `parsers.command` and records its `run(args, deps)`; `cli.py` runs whatever the chosen parser recorded and knows no action by name. `projects/` is the exception: one parser, because `shad projects [<group>] [<name>] [status]` is a list of names, so `projects/command.py::run` resolves them to `list`, `open` or `status`. The modules at a slice's root are what several actions need and must not diverge on. For `sessions/`: the snapshot format and file (`model.py`, `store.py`), which harness holds which conversation (`harness.py`, `live.py`), how rows and states are drawn (`render.py`), and the picker over live rows (`pick.py`). For `todo/`: the item format (`model.py`), the files (`store.py`), and the styling `list` and the panel share (`render.py`). For `config/`: the validated write (`store.py`), the raw-dict parse and queries (`raw.py`), and how `show` and `get` print a value (`render.py`); `edit` runs `validate` through its public name, as the todo panel runs `add_in_editor`. A new action is a new package; it reaches these through their public names and never another action's internals. Small duplication between actions, such as the five lines that run `$EDITOR` in `todo/add` and `todo/edit`, is left alone rather than extracted. Shared test fixtures live in the slice's `testing.py`, which no command imports.
- **The picker core is `picker.py`**: `select_one` and `select_many` are pure loops over an iterator of keys with a draw callback, so their tests feed a scripted key sequence. `pick_one` and `pick_many` wrap them in /dev/tty. They raise `NoTerminal` instead of returning None when there is no terminal, so a caller can tell that apart from a cancel: the session picker in `projects/open` treats it as a cancel, `sessions save` turns it into an error that points at `--all`.
- **The picker uses cbreak mode and redraws by moving up, not raw mode and cursor save/restore**: `tty.setraw` also clears OPOST, so a newline is a bare line feed; a panel line that fills the pane then puts the next line at the wrap column and tmux moves it down a row, so every line costs two. `tty.setcbreak` keeps output processing. A saved cursor position (`ESC[s`) is a screen row, so once a frame scrolls the screen, restoring it draws the next frame below the old one. `_Terminal.draw` instead counts the frame's rows and emits `erase(rows)`: carriage return, cursor up that many rows, clear to end of screen. That only holds while the frame is shorter than the terminal, which is why `sessions/render.py::window` cuts the list to the terminal height with "N more" indicators.
- **`sessions save`/`stop` selection**: `save` and `stop` take session or project names, `--all`, or `--pick`; there is no prompt and no picker without `--pick`, so both run without a terminal ([CLI-6]). `live.resolve_names` maps a name to running rows by the tmux session name, the project key, the base session name, or the display name — the one place that mapping lives, shared by both. `save` is all-or-nothing on names (an unmatched name is `no_such_session`, nothing written); `stop` is per-item (it kills what matched, reports what did not, and exits 1 via `no_such_session` when any name matched nothing). The session the command runs in is left out of `stop`, through `Tmux.current_session()` (`$TMUX`, then `display-message -p '#S'`), because killing it detaches the client mid-command. Whether a harness is still running is read from `pane_current_command` across every pane of the session, matched against the harness name, because the index of the harness pane depends on `oc_position`. `kill_session` passes `=<name>` so tmux never matches a prefix: `tin-shad` is a prefix of `tin-shad--cc-<uuid>`.
- **`sessions/store.py` writes only**: it holds `snapshot_path(cfg)` and the atomic `write`; the read is a slice query ([STATE-1]). `show` and `restore` read the file themselves and raise `no_snapshot` when it is missing; `save` reads it only to pre-check the picker's rows and tolerates its absence. `grep -n "def read" sessions/store.py` finds nothing.
- **`sessions/restore/plan.py` decides, `restore/command.py` creates**: `plan()` classifies every entry as resume, new, running or skipped and runs no tmux write; the one write is `layout.create_session`, which `restore/command.py` calls for each step whose `creation` is set. Keep it that way for the same reason `git/sync/plan.py` is kept pure. A saved id with no transcript is kept: the harness starts the new conversation under it, so the tmux name is stable across restores.
- **"Running" is decided by conversation id, not by tmux name**: `plan()` takes what `live.collect` found and treats an entry as running when any live session holds its id. The name restore would create often does not exist while the conversation is live: the live session was opened as `fresh-<epoch>`, or its id was superseded by `/clear` or `/resume`. A `session_exists` check on the computed name alone would start a second `claude --resume` process on a live conversation. `session_exists` is the second check, for a name that exists without a readable record.
- **`restore` opens kitty tabs through `sessions/restore/terminal.py`**: `plan.tab_targets` returns the (session, directory) pairs: every session that was attached at save except the one the current terminal takes, leaving out any that has a client now, because tmux mirrors one session across its clients. `terminal.current()` is `KITTY_WINDOW_ID` plus `kitten` on PATH; `open_tab` runs `kitten @ launch --type=tab --keep-focus`. Without a socket (`listen_on` in kitty.conf), `kitten @` writes a DCS sequence to the tty and waits for the reply; inside tmux the reply never comes, and kitten ignores SIGTERM, so `open_tab` passes a timeout and lets `subprocess.run` kill it. `_open_tabs` stops at the first failure, or every tab would wait out the timeout, and prints the `tmux attach-session` command for each session without a tab.
- **`shad git sync` layering**: the slice is a DAG — `run` and `model` are leaves, `refs` reads, `discover` resolves, `plan` decides, `apply` mutates, `command` orchestrates. `plan.py` is the safety boundary: it runs no git mutations, it only classifies. Keep it that way — a deletion rule that can also delete is much harder to test.
- **`shad git sync` ordering**: two orderings in `git/sync/command.py` are load-bearing. Fast-forward must run *before* branches are classified, or branches merged upstream are silently under-reported — and no test that fakes git output can catch it. Worktrees must be removed *before* branches are deleted, because `git branch -d` refuses a branch a worktree has checked out.
- **`shad git sync --switch`**: the only step in the command that writes to a working tree, which is why it is opt-in. It runs *after* the fast-forward (so the checkout lands on the new tip in one update) and *before* branches are classified (so the branch it leaves behind is no longer pinned and can be deleted in the same run). `fetch_and_plan` re-reads `worktree list` when a switch happens — HEAD moved, so the earlier read is stale. Every blocking condition skips with a reason; nothing stashes, discards, or detaches.
- **`shad git sync` gating**: fetch, prune, and fast-forward are applied immediately; only the branch and worktree deletions are gated, behind `--yes`. There is no confirmation prompt (`[CLI-6]`): without `--yes`, `sync_projects` reports the pending deletions and applies none. The report renders the applied steps in the past tense for that reason. `sync_projects` reports and returns; the entry point `run` calls `raise_for_failures`, which exits `1` on any per-project failure — `sync_failed` when all failed, `partial_failure` when some did (`[CLI-2]`). Rendering happens before the raise, so the per-project report reaches stdout and the error line reaches stderr.
- **Deleting a gone-upstream branch**: safe only when that upstream ref was pruned *in this run*, because pruning a ref deletes its reflog and its last-known OID with it. That OID is the proof the branch was fully pushed. This is why `--dry-run` fetches but never prunes, and why `plan.stale_upstreams()` has a separate dry-run path that asks the remote via `ls-remote` instead. Both of its paths filter on the `refs/remotes/<remote>/` prefix: the ref snapshots cover every remote, so without it a second remote's refs all read as stale.
- **`shad git panel` is read-only**: the only git write it performs is the fetch in `snapshot.collect`, and that fetch passes `prune=False` deliberately. Pruning a remote-tracking ref deletes its reflog and its last-known OID, which is the evidence `plan.stale_upstreams()` needs to prove a gone-upstream branch was fully pushed. A viewer that pruned would silently consume what the sync command depends on. `git/test_real_git.py::SnapshotTests::test_the_panel_fetch_does_not_prune` guards this.
- **`stash list` is not `for-each-ref`**: it belongs to the log pretty-format family, which does *not* interpret the `%00` escape the rest of the slice uses — it emits three literal characters. Use `LOG_SEP` (`%x00`) there and `FMT_SEP` (`%00`) everywhere else. `-z` then terminates each record with the same NUL that separates fields, so the output is one flat field stream and records are recovered by counting fields, not by splitting on a record separator. The date is `%ct`, not `%cr`, because the relative form is gettext-translated; `panel._age` formats the timestamp instead.
- **`run._is_read_only` special cases**: `worktree` and `stash` are both verbs whose `list` subcommand is a read while the rest mutate. A bare `args[0] in _READ_ONLY` would hand `GIT_OPTIONAL_LOCKS=0` to `stash drop`. Add new multi-verb commands the same way.
- **textual is imported lazily**: `git/panel/command.py::open_panel` imports `shad.git.panel.app` inside the function, not at module scope. `textual.app` costs roughly 100ms to import and every `shad projects <name>` and `shad git sync` would otherwise pay it. Keep every `textual` import inside `git/panel/app.py`.
- **Panel tests**: `git/test_panel.py` uses stdlib `unittest.IsolatedAsyncioTestCase` with textual's `App.run_test()`, so the suite needs no `pytest-asyncio`. The logic worth testing lives in `snapshot.py`, which is synchronous — keep it that way and keep the panel a thin view, or the testable surface moves into the async layer.
- **Panel sizing**: the pane is about 17 rows by 40 to 50 columns at the default `panel_percent`/`todo_percent`, because in the default layout the git panel shares the todo column. That is why the header is one line rather than a table, the nav column is a fixed 16 (12-char label + 2 padding + 1 border, or the labels wrap), and the stash age is `5m` rather than `5 minutes ago`.
- **All git goes through `shad.git.run.git`**: `projects/status/command.py` used to shell out with `subprocess.run(..., cwd=path)`. That path inherits `GIT_DIR`, so `shad projects <name> status` reported whichever repository invoked shad — a git hook, or a tmux pane started by one — instead of the project, and it had no timeout. It now uses `discover.head_branch`, `discover.is_clean`, `refs.latest_tag` and `refs.recent_commits`. `_capture` survives only for the non-git version probes (`python3 --version` and friends); do not route git through it again. `projects/status/test_command.py` asserts no `["git"` literal remains in the module.
- **The status dirty count changed with that migration**: `is_clean(untracked=True)` counts every untracked file, where `status --short` collapsed an untracked directory into one entry. An untracked directory holding two files now reads as two, which is what the "file(s)" label claims.
- **git output parsing**: always use plumbing with explicit formats, and decide from exit codes. Git messages are gettext-translated, `fetch.output = compact` rewrites ref names, and `git branch` layout depends on terminal width. A real NUL byte cannot be passed in argv, so the separator is an escape git expands — and the spelling depends on the command family: ref-filter (`for-each-ref`, `branch`, `tag`) takes `%00` (`FMT_SEP`), the pretty-format family (`log`, `show`, `stash list`, `reflog`) takes `%x00` (`LOG_SEP`). Neither accepts the other's, and neither reports the mismatch — `run._check_format_dialect` raises on it instead.
- **Completion input**: the completion script parses `shad config keys`, not `shad projects`. The latter prints ●/◆ bullets for humans. The script is generated from a template in `completion/command.py` with the `config/schema.py` enum values interpolated, and is installed by *sourcing* `shad completion bash`, never by pasting its text into a startup file — a pasted copy silently keeps completing an older command surface. `completion/test_command.py` drives the script in a real bash process against a fixture config, so a new subcommand that the script does not know about fails the suite.
- **Project identity**: a project is a *directory plus a tmux session*, not a repository — projects need not be git repos at all. Two projects on the same directory are rejected by `_reject_duplicate_paths` in `config/loader.py`, which is safe to fail hard on because it is a property of the config text alone. Two projects on different directories that resolve to one repository (linked worktrees) are legal, and `git/sync/command.py::_resolve` deduplicates them on `--git-common-dir` before any fetch runs. Do not conflate the two: two *clones* of one remote have different common dirs and different local branches, so both must be synced.
- **Config path resolution**: never hard-code `~/.config/shad/shad.toml`. Call `config/loader.py::config_path()`, which applies `$SHAD_CONFIG`, then the per-OS default from `default_config_dir()`, then an existing legacy `~/.config/shad` file. `cli.main()` resolves `--config` once into `Deps.config_file`, and `Deps.config` loads that file on first use; the config actions and `init` edit `config_file`, every other command reads `config`, so readers and writers cannot disagree on the file. `default_config_dir()` branches on `sys.platform`, not `os.name`, because pathlib dispatches on `os.name` and a test that patched it could not construct a path at all.
- **`config/store.py` writes only**: it holds `commit`, `write_value` and `add_project`, and reads the file only to form the text it is about to replace ([STATE-1]). The actions read and parse the file themselves through `config/raw.py`, the pure raw-dict codec (`parse`, `lookup`, `project_paths`, `MISSING`). `grep -n "def read" config/store.py` finds nothing. A missing file is each action's own `no_config_file`; `keys` tolerates its absence.
- **Config writes**: the stdlib has no TOML writer and shad adds no dependencies, so `config/toml_edit.py` edits the file as text to keep comments. It handles scalar values and single-line arrays of scalars, and rejects multi-line values. Every write is parsed with `tomllib` and loaded with `config.loader.load()` in a temporary file first, then replaced into position through `atomic.replace`. `config/store.py::write_value` is the entry point for a key outside the `set` schema (`shad todo label` uses it for `[todo] labels`), and `add_project` is the one `shad init` writes through, so a project path with a quote or a backslash is escaped and the file stays valid TOML. The write strategy is last-writer-wins, named in `commit`'s docstring (`[CONC-3]`).
- **Todo files are the source of truth**: `shad todo` keeps one file per item at `store.todo_dir(cfg)/<item key>.md` — a header block, a blank line, the body. `todo/model.py::parse` never raises: a hand edit that leaves an unknown status or label is surfaced by `problems()`, and a header shad does not define rides along in `Item.extra`. `serialize(parse(text))` must round-trip the body byte for byte, because a status change from the panel rewrites the file. `store.add` creates with `O_EXCL`, so two adds of one key cannot both win; every other write touches one file through a temp file and `os.replace`. There is no lock, and nothing may be added that reads one file to write another.
- **`shad todo add` without a title**: `todo/add/command.py::add_in_editor` writes `model.template()` to a file in the temporary directory, not the data directory, so the list and the panel never show an unfinished draft. The template's help lines start with `#`. `parse()` skips them only because `_HEADER` requires a header name to start with a letter, so do not loosen that pattern. A draft that `store.add` rejects is reopened with the reason written at the top as `#` comment lines, until the draft is valid or left empty; there is no prompt, and the draft is not kept. The command refuses to open an editor when stdin is not a terminal, because an editor reading a pipe blocks the caller.
- **The panel's `a` key and `App.suspend()`**: `todo/panel/app.py::action_add` calls `add_in_editor` inside `self.suspend()`, because the editor uses the terminal. In textual 8.2, `suspend()` resumes the app only when its block exits normally. An exception that leaves the block leaves the panel suspended, and it stops reading keys. `action_add` therefore catches `ShadError`, `KeyboardInterrupt` and `EOFError` inside the block. `todo/panel/test_app.py` replaces `suspend` with a recorder that has the same behavior, and asserts that the app resumed.
- **Data dir is not config dir**: the root resolves the per-OS data directory once (`config.loader.default_data_dir(os.environ)`) and injects it as `Deps.data_dir`; `load()` carries it into `Config.data_dir`. The todo files are `Config.todo_dir` (`[todo] path` when set, else `data_dir / "todo"`) and the snapshot is `cfg.data_dir / "sessions.json"` (`sessions.store.snapshot_path(cfg)`). The data dir never goes through `config_path()`: a config directory is often a dotfiles repository, and these files must not be dragged into one by default. `[todo] path` must be absolute after `~` expansion; `config.loader.load()` rejects a relative path because it would resolve against each pane's cwd. A unit test sets `Config.data_dir` or `Config.todo_path`; the data dir's own branches are tested on `default_data_dir(env)` with a fake environment.
- **`shad todo` has one list, not one per project**: no action reads cwd or takes a project, and the layout sends a bare `shad todo panel` to every project session, so every session shows the same files. `store._item_files` lists only the `.md` files directly in the todo dir; files in a subdirectory are not read.
- **The todo layouts address panes by id**: with `todo_panel` on, `layout.py::_layout_with_todo` captures `#{pane_id}` from each `split-window -P -F` and never uses `session:0.N`, because a fourth split makes every later index depend on the order of the earlier ones. The layouts without a todo pane still use `session:0.N`; when `git_panel` is off they skip the git split, which shifts the index of the harness pane under `bottom`.
- **Panel switches are TOML booleans**: `config.loader.load()` rejects a `git_panel` or `todo_panel` that is not `true` or `false`, because a quoted `"false"` is truthy. `todo_percent` is 1-99; `todo_panel = false` is the only way to turn the todo pane off.
- **textual is imported lazily, again**: `todo/panel/command.py::run` imports `shad.todo.panel.app` inside the function. `todo/panel/test_command.py` reads the module source and asserts the import is indented. Keep every `textual` import inside `todo/panel/app.py`.
- **A textual `App` subclass must not set `self._name`**: `DOMNode.__init__` owns that attribute and `App.name` reads it. mypy catches the collision only when the value type differs.
- **Todo panel polling**: the panel calls `store.signature()` once a second and reloads on any change — name, mtime, or size of any item file. `load()` is synchronous because the directory is tens of files; do not move it to a worker. The panel's tests call `app.poll()` directly rather than waiting out the interval.
- **Completion input for todo**: the script parses `shad todo list --keys` and `shad todo label list`, both one plain word per line. The keys call carries `--config` from the command line, so the keys come from the `[todo] path` of the config the command will read. `shad todo list` without `--keys` is a rich table for humans and is not safe to parse.
- **Errors are raised, never printed, below the root**: a slice raises `ShadError.<category>(code, message)` from `errors.py`, with the six `[ERR-5]` categories and a `code` the slice owns. `cli.main` is the only place that renders one: `<code>: <message>` on stderr, `usage` exits 2 and every other category 1, the traceback under `--debug`, and any other exception becomes `internal`/`unexpected`. A stdlib or subprocess failure is converted where it occurs: `tomllib.TOMLDecodeError` in `config/loader.py::load`, `config/raw.py::parse` and `config/store.py::commit`, tmux in `tmux.py::Tmux.run`, git in `git/run.py`, an editor exit in `editor.py::Editor.open`. `NoTerminal` (picker) and `NotUsable` (git discover) are control flow caught inside their packages; a `NoTerminal` that reaches a command boundary becomes `infrastructure`/`no_terminal`. The messages are one line, because the contract is one line.
- **`--debug` and `--json` are parent parsers with `default=argparse.SUPPRESS`**: every parser is built through `parsers.command` or `parsers.group`, which add both parents, so each flag is accepted before and after the subcommand. The default is SUPPRESS because argparse applies a subparser's defaults after the root has parsed, and a `False` default on the subcommand would overwrite a flag given before it; `main` reads them with `getattr`. Diagnostics go through the `Trace` the root constructs from `--debug` and injects; no module writes to stderr on its own, and `warnings.warn` is not used.
- **A read returns a result; the root presents it**: a read command's `run` returns a frozen dataclass whose fields are JSON values (`Project`, `Entry` and `Commit` ride along; `Output.json` stringifies a `Path`), and its `register` passes `render`, the function that prints it as text. The presence of `render` on the parser is what makes `--json` apply: the root encodes `dataclasses.asdict(result)` or calls `render`, and raises `no_json` for a parser without one before anything runs. A command that returns a result must not print on its way; a mutation prints through `deps.out` and returns None, and a command that hands the terminal over returns the exit status. `shad projects` is one parser for list, open and status, so `projects/command.py` raises `no_json` itself when the names resolve to an open, and `todo list --keys` and `config show --raw` do the same for their plain forms.
- **Output is injected; no module holds a Console**: the root constructs one `Output` per run and every command prints through `deps.out` (`print` on stdout, `note` on stderr for what the run reports: a session `save` cannot record, a tab `restore` cannot open, a problem `edit` finds). `out.plain` writes a line byte for byte; the commands whose plain output is the machine form (`config path`, `config keys`, `todo list --keys`, `todo label list`, `completion bash`, `config show --raw`) use it, because `Console.print` reads `[todo]` as markup and wraps a long line. The two `Console(file=buf, ...)` in `cheat` and `picker.py` render to a string for a popup and a tty; they are not stdout. `grep -rn "Console(" src/shad` should find only those and `output.py`.
- **Root-level modules are crosscuts, each named for its concern, and the ones that read the environment are constructed by the root**: `Tmux(os.environ)` and `Editor.from_env(os.environ)` are built once in `cli._dispatch` and travel in `Deps`; `tmux.inside` (from `TMUX`) decides attach versus switch-client, and `cheat` reads it rather than the environment. A slice gets tmux and the editor from `deps`, never by import. `addressing`, `style`, `atomic`, `picker`, `layout` and `harness` are pure or stateless and are imported. Each crosscut's docstring says whether it is shared-and-safe or per run (`[CONC-2]`); `git/run.py` is shared across the sync pool because it builds each call's environment afresh. A unit test hands a slice `testing.deps(cfg, tmux=Mock(spec=Tmux))` and configures the methods it expects. There is no `shared/` and no module imports a `_name` from another module; the tests of a module may.
- **A package publishes through `__init__.py`, and `register` there is a lazy wrapper**: `shad.git` publishes the six names `projects/status` reads, `shad.todo` the four the panel's keys run, and every package its `register`. The wrapper imports `<package>.command` on call, because `config` and `todo` import each other's modules (`config show` and `get` read `todo.store.todo_dir` until T3.4) and an eager `__init__` import of the whole command tree makes `import shad.config.loader` from a `todo` module a cycle. For the same reason a consumer imports `shad.config.loader` directly: it is the module the package keeps for the purpose.
- **`git/` is the tool crosscut at its root and two commands under it**: `run`, `refs`, `discover`, `apply` and `model` are what `sync/` and `panel/` share and what `projects/status` reads through `shad.git`; `apply` stays at the root because the panel's fetch is one of its commands. `sync/plan.py` is the safety boundary; `panel/snapshot.py` is the panel's one reading.
- **`harness.py` is the one place a harness is described**: `Claude(home)` and `Opencode(home)` hold where each program keeps its files, `recorded(project_path)` lists its conversations, `is_uuid` identifies one, and `resume_target`/`fresh_target` write its command lines. The root builds one `Harnesses.from_env(os.environ)` and injects it; `projects/open/sessions.py::pick_target` draws the picker over `harness.recorded` and asks, and `sessions/live.py`/`restore/plan.py` go through `harnesses.for_harness`. A unit test constructs a `Claude`/`Opencode`/`Harnesses` on a temporary home, or sets `.projects_dir`/`.db_path`.
- **`shad init` is non-interactive by default**: `--path DIR` adds the project from flags (`--group`, `--key`, `--session`, `--harness`); `--wizard` prompts. It writes only through `config/store.py::add_project` ([STATE-5]) and reads the file through `config/raw.py` to stay idempotent: a re-add of the same resolved path is a no-op (the file stays byte-identical), and a different path for an existing key is `conflict`/`project_exists`. `--install-deps` installs the harness in use (`--harness`, else `[defaults] harness`, read tolerantly so it works before any config exists): tmux always, opencode when it is the harness. It never installs Claude Code — shad bundles no installer — and instead checks `PATH` and points at the official one. The Fedora-only, sudo, SHA-256 and x86_64 guards stay on the opencode path.
- **`config/schema.py` is the one definition of `shad.toml`**: every key with its kind, range, default and description. `config/loader.py::load` validates each `[defaults]` value through `schema.check`, so `load` rejects every value `config set` rejects — a `panel_percent` of 500 is `invalid_config` at load, not a crash in `tmux split-window` later. `shad init` starts a new file with `schema.defaults_block()` and a test holds `shad.example.toml` to the schema's defaults. Add a setting by adding a `Field`; nothing else enumerates the keys.
- **Trust boundary**: the invoking user and their files (`shad.toml`, the todo files, the snapshot) are trusted; other programs' files and the network are not, and are validated where read (`[TRUST-1]`, `[TRUST-2]`; README "Trust boundary"). The one file-sourced value that reaches a shell is a conversation id, so `harness.is_uuid` gates it at every read: `sessions/model.py::parse` rejects a non-uuid `session_id` as `invalid_snapshot`, and `harness.Claude._process_record` drops a record whose `sessionId` is not a uuid. Project keys typed into panes come from the trusted config.
- **The root reads the environment; the crosscuts own each value**: `cli._dispatch` builds `Tmux(os.environ)`, `Editor.from_env(os.environ)`, `Harnesses.from_env(os.environ)`, resolves `config_path(os.environ)` and `default_data_dir(os.environ)`, and injects them in `Deps`. `grep -rn "os.environ|Path.home()" src/shad` finds only `cli.py` and the crosscuts that own a value: `config/loader.py` (the config file and the per-OS dirs), `harness.py` (HOME, for the harness files), `git/run.py` (the scrubbed git subprocess environment) and `sessions/restore/terminal.py` (`KITTY_WINDOW_ID`). No command module reads the environment.
- **A panel is the presentation boundary while it runs**: the todo panel's keys call the functions `todo/__init__.py` publishes (`set_status`, `remove`, `add_in_editor`, `edit_in_editor`) rather than the store, so a key cannot bypass what the command checks, and a `ShadError` from one is shown as a notification with its code and category, never raised out of the app. The git panel puts a failed reading's code and category in its header. A failure before a panel opens (`no_repository`, `ambiguous_target`) is raised as usual and the root renders it.
- **Pane sizes are `-l N%`, never `-p N`**: tmux 3.4 (Ubuntu 24.04) rejects `split-window -p` with "size missing", so `shad projects` could not build a layout there. `layout.py::_size` spells the size as `-l N%`, which every tmux since 3.1 accepts. The behavior tests run the layout on CI's tmux; the layout unit tests assert the spelling.
